# Отчёт о тестировании

Команды в этом документе выполняются из корня репозитория, если не указано иное.

## Тестирование и производительность

### Полная инструкция по запуску тестов (Windows / PowerShell)

#### 1. Откройте проект и установите зависимости

Откройте корневую папку репозитория в VS Code и выберите **Terminal → New Terminal**. Все команды ниже рассчитаны на PowerShell. В начале убедитесь, что вы находитесь в папке проекта, где лежат `README.md`, `backend` и `neo4j`.

Необходимы Python, pip и Docker Desktop для полного набора. Для установки в отдельное окружение выполните:

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Виртуальное окружение не нужно активировать: в следующих командах используется его Python. Если `python` не найден, установите Python и откройте терминал заново. Для PDF-теста нужен PDF из корня репозитория `Мельничек 2_раздел.pdf` и файл `neo4j/parser_service/parser/extract_text.py`.

#### 2. Задайте тестовые настройки

Оставаясь в папке `backend`, выполните:

```powershell
$env:NEO4J_URI = 'bolt://127.0.0.1:17690'
$env:NEO4J_USER = 'neo4j'
$env:NEO4J_PASSWORD = 'testpassword123'
$env:NEO4J_DATABASE = 'neo4j'
$env:GEMINI_API_KEY = 'test-key'
$env:QUERY_CLASSIFIER_USE_LLM = 'false'
```

Это настройки только для текущего окна PowerShell. `test-key` — заглушка; настоящий ключ и доступ в Gemini для автоматических тестов не нужны. Файл `.env` при этом не меняется. После открытия нового терминала повторите эти переменные.

#### 3. Запустите тесты без базы Neo4j

Из папки `backend`:

```powershell
.\.venv\Scripts\python.exe -m pytest `
  tests/test_document_service.py `
  tests/test_boundaries_and_failures.py `
  tests/test_real_pdf.py `
  tests/test_api.py `
  tests/test_classifier.py `
  tests/test_llm_client.py `
  tests/test_prompt_builder.py `
  tests/test_query_service.py -v
```

Здесь `-v` показывает каждый тест. Эти проверки используют подменённые зависимости и временные файлы; для них не требуется запущенная Neo4j. `test_real_pdf.py` действительно извлекает текст из PDF, но импорт в базу в нём подменён. В нашем запуске этот набор содержал 59 проверок; число и время могут измениться при изменении проекта.

Чтобы запустить только один файл, например проверки загрузки документов:

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_document_service.py -v
```

#### 4. Создайте отдельную тестовую Neo4j — один раз

Запустите Docker Desktop и дождитесь его готовности. Возвратитесь из `backend` в корень проекта:

```powershell
cd ..
docker info --format '{{.ServerVersion}}'
```

Если сервер Docker не отвечает, дождитесь запуска Docker Desktop и повторите проверку. При **первом** запуске создайте отдельный контейнер и том:

```powershell
docker run -d --name course-pytest-neo4j -p 127.0.0.1:17690:7687 -e NEO4J_AUTH=neo4j/testpassword123 -v course_pytest_neo4j_data:/data neo4j:5-community
```

Если порт 17690 уже занят, используйте другой свободный порт в левой части параметра `-p`, например `17691:7687`, и измените `NEO4J_URI` соответственно. Если контейнер с таким именем уже существует, не создавайте его повторно: проверьте, что это ваша тестовая база, и запустите `docker start course-pytest-neo4j`.

Дождитесь готовности Neo4j — запуск может занять некоторое время. Повторяйте команду, пока она не вернёт `ready` и `1`:

```powershell
docker exec course-pytest-neo4j cypher-shell -u neo4j -p testpassword123 'RETURN 1 AS ready'
```

Загрузите в **отдельную тестовую** базу ограничения и начальные данные из корня проекта:

```powershell
docker cp neo4j/cypher/constraints.cypher course-pytest-neo4j:/tmp/constraints.cypher
docker cp neo4j/cypher/seed.cypher course-pytest-neo4j:/tmp/seed.cypher
docker exec course-pytest-neo4j cypher-shell -u neo4j -p testpassword123 -f /tmp/constraints.cypher
docker exec course-pytest-neo4j cypher-shell -u neo4j -p testpassword123 -f /tmp/seed.cypher
```

Убедитесь, что в новой базе загружены **25 узлов и 28 связей**:

```powershell
docker exec course-pytest-neo4j cypher-shell -u neo4j -p testpassword123 'MATCH (n) RETURN count(n) AS nodes'
docker exec course-pytest-neo4j cypher-shell -u neo4j -p testpassword123 'MATCH ()-[r]->() RETURN count(r) AS relationships'
```

Это контрольные значения для новой базы с одним seed. Если в том уже импортировались документы, значения могут отличаться. Не выполняйте эти действия на основной или чужой базе.

#### 5. Запустите полный набор

Снова перейдите в `backend`. В том же терминале переменные из шага 2 сохраняются:

```powershell
cd backend
.\.venv\Scripts\python.exe -m pytest -q
```

Для подробного списка замените `-q` на `-v`. Интеграционные тесты обращаются к реальной тестовой Neo4j; Gemini в них подменён. У нас на свежей seed-базе прошёл **81 тест**. Предупреждения об устаревающих настройках asyncio в Python 3.14 не означают провал теста. Если появился `FAILED`, прочитайте текст ошибки: количество пройденных тестов само по себе не гарантируется при изменениях кода или данных.

После работы можно остановить контейнер, не удаляя том и данные:

```powershell
docker stop course-pytest-neo4j
```

При следующем запуске откройте Docker Desktop, выполните `docker start course-pytest-neo4j`, дождитесь команды `RETURN 1`, задайте переменные из шага 2 и запустите pytest. Повторно создавать контейнер и загружать seed обычно не нужно. Если данные менялись, проверьте состояние тестовой базы перед сравнением результатов.

#### Как читать результат

`passed` — проверка прошла, `failed` — обнаружено несоответствие, `skipped` — проверка пропущена. Время в строке pytest относится к выполнению набора, а не к скорости ответа пользователя. Для реальных замеров Gemini нужен отдельно запущенный backend с настоящим ключом и работающей базой; такие замеры расходуют квоту и описаны далее. Не вставляйте настоящий ключ в отчёт или репозиторий.

### Как измерить объём базы и нагрузку

Для реальной нагрузки отдельно запустите backend и Neo4j, загрузите начальные данные и документы, дождитесь индексации и укажите рабочий ключ Gemini. Указанные выше команды pytest запускают тесты, а не постоянно работающий backend. В Neo4j Browser выполните отдельно:

```cypher
MATCH (n) RETURN count(n) AS nodes;
MATCH ()-[r]->() RETURN count(r) AS relationships;
MATCH (n) WHERE n.source IS NOT NULL RETURN count(DISTINCT n.source) AS distinct_node_sources;
```

Зафиксируйте результаты, название базы, состав и число загруженных документов. Число источников в свойствах узлов не обязательно равно числу документов. Для размера на диске измерьте размер каталога или Docker volume базы отдельно: количество узлов и связей не является размером в байтах.

В отдельном тестовом окружении выполните из `backend`:

```powershell
python scripts/load_query.py --url http://localhost:8000 --requests 20 --concurrency 1 --question "What is BERT?"
python scripts/load_query.py --url http://localhost:8000 --requests 50 --concurrency 5 --question "What is BERT?"
python scripts/load_query.py --url http://localhost:8000 --requests 100 --concurrency 10 --question "What is BERT?"
```

Скрипт отправляет реальные POST `/query`, показывает количество ответов по HTTP-статусам и ошибок соединения, успешные ответы в секунду и среднюю, p50, p95, p99 задержки успешных запросов. Он возвращает ненулевой код при любой ошибке. Задержка измеряется от отправки до получения ответа, без времени ожидания свободного слота; производительность — успешные ответы, делённые на полное время серии. Серии имеют фиксированное число запросов и не доказывают длительную устойчивость. Повторите серии, зафиксируйте аппаратную конфигурацию сервера и клиента, версии, число записей, модель, квоты Gemini, параметры параллельности и ошибки. Максимальную устойчивую нагрузку определяйте по заранее выбранным пределам ошибок и p95 на более длительных сериях; эти команды сами по себе не устанавливают предел пользователей. Вызовы Gemini могут расходовать квоту и средства.

### Реальные запросы к Gemini и нагрузка, 24.11.2026

Измерялся локальный backend через HTTP `127.0.0.1:18000` и отдельная Neo4j 5.26.32 через Bolt `127.0.0.1:17687` с указанными выше 25 узлами и 28 связями. Backend — один процесс Uvicorn на Windows, клиент и сервер на одной машине, Python 3.14.3, модель **gemini-3.1-flash-lite** через внешний Gemini API, правила классификации (`QUERY_CLASSIFIER_USE_LLM=false`), парсер загрузки отключён, тайм-аут Gemini 30 с и до двух повторов. Проект Google использовал Free tier; данные о фактических лимитах проекта не измерялись. Задержка включает Neo4j, сеть, генерацию и возможные повторы. Задержки и доступность зависят от внешнего сервиса и сети.

Модель проекта по умолчанию `gemini-2.5-flash` вернула HTTP 404: Google сообщил, что она недоступна новым пользователям; backend вернул клиенту 502. Рекомендованная Google `gemini-3.8-flash` также не дала успешного ответа в первой попытке приложения: внешний API отвечал 503, а backend вернул 502 через **43,109 с** с повторами. Прямой пробный запрос к `gemini-3.1-flash-lite` ответил HTTP 200 за **6,89 с**, после чего эта модель использовалась для остальных измерений. Модель менялась переменной окружения только на время тестового запуска.

Последовательные одиночные запросы через backend:

| Вопрос | HTTP | Время, с | Результат |
| --- | ---: | ---: | --- |
| What is BERT? | 502 | 33,685 | Ответ не получен |
| What is BERT used for? | 502 | 34,012 | Ответ не получен |
| Compare BERT and GPT and explain their tasks and methods. | 200 | 2,000 | `comparison`, `from_kb=true`, 819 символов ответа |

Короткие серии с одинаковым вопросом `What is BERT?`, без отдельного прогрева; замер через `backend/scripts/load_query.py`. Параллельность означает одновременно выполняемые HTTP-запросы, а не число зарегистрированных пользователей. Время серии включает ошибки; среднее и перцентили вычислены только по успешным ответам, по ближайшему рангу.

| Одновременно | Запросов | Успешно / ошибки | Длительность, с | Успешных ответов/с | Среднее успешных, мс | p50, мс | p95, мс |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 3 | 2 / 1 (HTTP 502) | 50,580 | 0,040 | 8 788,2 | 8 209,5 | 9 366,8 |
| 2 | 4 | 4 / 0 | 33,985 | 0,118 | 10 163,4 | 2 150,1 | 31 834,4 |
| 4 | 4 | 3 / 1 (HTTP 502) | 7,369 | 0,407 | 3 658,1 | 1 897,6 | 7 360,9 |

Это отдельные короткие серии, а не измерение максимальной устойчивой пропускной способности. При 2–4 успешных ответах перцентили статистически ненадёжны; результаты серий несопоставимы как доказательство масштабирования, поскольку внешний сервис отвечал нестабильно и длительность серий различалась. Нельзя утверждать, что система стабильно обслуживает 0,407 запроса/с или определённое число пользователей. Для определения предела нужны повторные длительные серии на контролируемом окружении с заранее заданными допустимыми p95 и долей ошибок. Квоты Gemini могут ограничивать число запросов и возвращать 429 отдельно от ограничений приложения; 502 в таблице не следует автоматически считать ошибкой квоты. Тарифы и доступность моделей: [Google Gemini API pricing](https://ai.google.dev/gemini-api/docs/pricing); фактические лимиты проекта смотрите в AI Studio.

Для повторения запуска backend из `backend` укажите переменные `NEO4J_URI`, `NEO4J_USER`, `NEO4J_PASSWORD`, `GEMINI_API_KEY` и `GEMINI_MODEL=gemini-3.1-flash-lite`; ключ не записывайте в отчёт. Скрипт нагрузки и примеры вызова описаны выше.

**Проверка границ через работающий API.** Неподдерживаемое расширение и пустой PDF получили HTTP 400; повреждённый PDF получил HTTP 400 за 5,169 с; пустой запрос, запрос длиной 501 символ и неподдерживаемый язык получили HTTP 422. Проверены отдельные примеры, а не все варианты некорректных данных. Повреждённый PDF остался на диске после ошибки обработки.

**Повторные серии с Gemini на пополненной базе.** Вопрос `What is BERT?`, модель `gemini-3.1-flash-lite`, классификация правилами, один локальный процесс backend; Free tier, `LLM_TIMEOUT_SECONDS=20`, `LLM_MAX_RETRIES=0` (в отличие от предыдущего запуска), клиентский тайм-аут 30 с. Каждая строка — одна серия, без отдельного прогрева. HTTP 200 считается успешным транспортным ответом, качество текста вручную не оценивалось. Значения задержек относятся только к успешным ответам; RPS = число успешных ответов / время всей серии.

Всего 22 попытки: 8 HTTP 200 и 14 HTTP 502. В журналах были ответы Gemini HTTP 503 и тайм-ауты; по одному коду HTTP 502 нельзя однозначно определить причину каждого отказа. Эти измерения показывают фактически наблюдавшуюся производительность в указанных условиях, а не предел приложения или число пользователей, которое оно устойчиво выдерживает. Длительного теста и повторов серий недостаточно для такого вывода; при доле ошибок 50–83,3% ни один из трёх уровней нельзя считать надёжно обслуживаемым. Метрики 95-го процентиля на 1–4 успешных запросах ненадёжны. Предел квоты конкретного проекта не установлен и может меняться; 502 не доказывает исчерпание квоты. Ключ и ответы модели в отчёт не включены.

**Обнаруженные проблемы и приоритет исправления:**

1. **Высокий:** при недоступной Neo4j реальный запрос возвращает HTTP 500 вместо предусмотренного HTTP 503; `ServiceUnavailable` не преобразуется в `Neo4jConnectionError`.
2. **Высокий:** модель `gemini-2.5-flash` по умолчанию недоступна для нового аккаунта и приводит к HTTP 502; необходимо обновить конфигурацию доступной моделью и проверять доступность.
3. **Высокий для достоверности источников:** импорт устанавливает единственное свойство `source` на всех совпавших узлах. После AI-PDF из 25 исходных узлов 12 получили новый источник; повторная загрузка того же файла через API заменила источник у 17 узлов именем новой загрузки. История исходных документов при этом теряется. Нужна модель множественных источников или отдельных связей с документами.
4. **Средний:** повреждённый PDF отклоняется, но сохранённый файл остаётся в каталоге загрузок после сбоя парсера. Нужна политика очистки неудачных загрузок.
5. **Ограничение извлечения:** первый PDF дал 0 сущностей и 0 связей, тематический — 17 сущностей и 0 связей. Само по себе это не доказывает ошибку извлечения без эталонной разметки, но статус `indexed` не гарантирует полезного наполнения базы.

После импорта выполнен полный `pytest -q`: **81 тест прошёл за 2,74 с**, два предупреждения Python 3.14 об устаревающих настройках asyncio. В интеграционных тестах используется реальная тестовая Neo4j и подменённая LLM. Производительность PDF и Gemini оценивалась отдельно описанными ручными экспериментами. Не выполнялись полная проверка безопасности, оценка точности RAG на размеченных вопросах, нагрузка в течение длительного времени, многопользовательская UI-проверка и проверка восстановления после сбоя; утверждать полное покрытие системы нельзя.

**Проверка frontend:** Node.js 24.15.0, npm 11.12.1. Чистая установка `npm ci --no-audit --no-fund` завершилась ошибкой `EUSAGE`: package-lock содержит несогласованные записи зависимостей `@emnapi/*`. Это дефект воспроизводимости установки на указанной версии npm; источник несогласованности требует отдельного анализа. После `npm install --no-package-lock --no-audit --no-fund` команды `npm run lint` и `npm run build` выполнились успешно (Vite 8.3.8; сборка Vite сообщила 290 мс). Установка без lock-файла может разрешить другие версии пакетов, поэтому успех не подтверждает воспроизводимость `npm ci`. Проверка браузерного интерфейса пользователем не проводилась.
