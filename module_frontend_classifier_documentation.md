# Документация по модулю интерфейса и классификации запросов

## 1. Общие сведения

В рамках курсового проекта реализован модуль пользовательского взаимодействия и классификации запросов для справочной RAG-системы по технологиям искусственного интеллекта.

Рабочее название интерфейса:

**RAG-справочник по ИИ**

Модуль обеспечивает ввод пользовательского запроса, передачу запроса в backend, отображение результата обработки, а также демонстрацию этапов классификации и использования базы знаний.

Основная цель реализованной части — предоставить удобный интерфейс для работы с системой и обеспечить корректное определение типа пользовательского запроса с использованием LLM и резервной rule-based логики.

---

## 2. Зона ответственности реализованного модуля

Реализованная часть включает два основных направления:

1. **Пользовательский интерфейс на React**  
   Интерфейс предназначен для взаимодействия пользователя с RAG-системой.

2. **Механизм классификации пользовательского запроса**  
   Классификация выполняется по схеме LLM-first с fallback на правила.

Таким образом, модуль отвечает не только за визуальное отображение результата, но и за важный этап обработки запроса — определение его типа.

## 4. Общая схема работы

Общая последовательность обработки запроса:

```text
Пользователь вводит запрос
↓
React UI отправляет запрос в backend
↓
Backend выполняет предварительную обработку
↓
Запрос классифицируется через LLM
↓
При недоступности LLM используется rule-based fallback
↓
Backend определяет тип запроса и сущности
↓
Выполняется поиск контекста в базе знаний
↓
Формируется ответ
↓
React UI отображает результат
```

## 7. Классификация пользовательского запроса

Одним из ключевых элементов реализованной части является классификация пользовательского запроса.

Поддерживаемая схема:

```text
LLM-first classification
+
rules fallback
```

Это означает, что система сначала пытается определить тип запроса с помощью LLM. Если LLM недоступна, возвращает некорректный результат или результат не соответствует допустимым типам, используется резервный классификатор на основе правил.

---

## 8. Поддерживаемые типы запросов

Классификатор поддерживает следующие типы:

| Тип | Назначение |
|---|---|
| `definition` | Запрос на определение термина |
| `comparison` | Запрос на сравнение технологий, моделей или методов |
| `capabilities` | Запрос о назначении или возможностях технологии |
| `methods` | Запрос о методах, подходах или алгоритмах |
| `recommendation` | Запрос на рекомендацию инструмента или подхода |
| `unknown` | Тип не определён |

Примеры:

```text
Что такое Transformer? → definition
Чем BERT отличается от GPT? → comparison
Для чего используется BERT? → capabilities
Какие методы использует GPT? → methods
Какой инструмент выбрать для NLP? → recommendation
```

---

## 9. LLM-классификация

LLM используется для более гибкого определения типа запроса.

Преимущества LLM-классификации:

- лучше понимает естественный язык;
- может классифицировать запросы с разной формулировкой;
- не ограничивается только ключевыми словами;
- повышает качество обработки пользовательских вопросов.

Результат LLM-классификации возвращается в backend и далее отображается в интерфейсе.

В UI источник классификации отображается как:

```text
Классификация: LLM
```

---

## 10. Rule-based fallback

Для устойчивости системы сохранён резервный классификатор на основе правил.

Он используется в случаях, когда:

- LLM недоступна;
- LLM вернула неподдерживаемый тип;
- ответ LLM не удалось корректно обработать.

В UI такой результат отображается как:

```text
Классификация: Rules fallback
```

Таким образом, даже при недоступности LLM система сохраняет возможность определить тип запроса и продолжить обработку.

## 11. Изменения на стороне backend, связанные с классификацией

Для поддержки классификации и отображения результата были внесены изменения в backend.

Основные файлы:

```text
backend/app/services/classifier.py
backend/app/services/query_service.py
backend/app/schemas/query.py
backend/app/schemas/ask.py
backend/app/routers/query.py
```

### 11.1. `classifier.py`

Добавлена логика LLM-first классификации с fallback на правила.

Общая идея:

```text
1. Выполнить rule-based анализ для извлечения базовых признаков.
2. Если LLM-классификация включена, отправить запрос в LLM.
3. Если LLM вернула корректный тип, использовать его.
4. Если LLM недоступна, вернуть результат rule-based классификатора.
```

### 11.2. `query_service.py`

В сервисе обработки запроса используется новая логика классификации:

```text
classify_with_llm_fallback
```

Это позволяет backend автоматически выбирать между LLM и rules.

### 11.3. Схемы ответа

В response-схемы добавлено поле:

```text
classification_source
```

Оно показывает, каким способом был определён тип запроса.

Пример:

```json
{
  "query_type": "comparison",
  "classification_source": "llm"
}
```

## 14. Формат ответа от `/query`

Пример ответа:

```json
{
  "answer": "BERT и GPT являются моделями на основе архитектуры Transformer...",
```

| Поле | Назначение |

| `source_entities` | Найденные сущности |
| `from_kb` | Признак использования базы знаний |
| `classification_source` | Источник классификации |

## 15. История запросов

В интерфейсе реализована история последних запросов.

История хранится локально в браузере через:

```text
localStorage
```

Сохраняется до 10 последних запросов.

Для каждого элемента истории сохраняется:

```text
текст запроса
язык запроса
тип запроса
найденные сущности
ответ
источник классификации
дата и время
```

История используется для удобного повторного просмотра и быстрого возврата к предыдущим запросам.

## 16. Загрузка PDF через интерфейс

В интерфейсе реализована загрузка PDF-документа.

Пользователь выбирает PDF-файл, после чего frontend отправляет его на endpoint:

```http
POST /documents/upload
```

После обработки UI обновляет список источников базы знаний.

В интерфейсе отображается краткий статус обработки. Подробный технический лог скрыт в раскрывающемся блоке.

Это позволяет сохранить интерфейс аккуратным и не перегружать пользователя технической информацией.

## 18. Запуск backend и Neo4j

Открыть терминал в корне проекта, где находится файл:

```text

```

Запустить контейнеры Neo4j и backend:




```text

```

Neo4j Browser доступен по адресу:

```text
http://localhost:7474
```

Данные для входа в Neo4j Browser:

```text
login: neo4j
password: password123
```

## 19. Инициализация базы знаний

После запуска Neo4j необходимо загрузить ограничения и начальные seed-данные.

Выполнить в корне проекта:

```powershell
docker exec neo4j cypher-shell -u neo4j -p password123 -f /cypher/constraints.cypher
```

Затем выполнить:

```powershell
docker exec neo4j cypher-shell -u neo4j -p password123 -f /cypher/seed.cypher
```

После загрузки seed-данных можно проверить список источников:

```powershell
Invoke-RestMethod http://localhost:8000/documents
```

В списке источников должен отображаться базовый источник:

```text
manual_seed
```

Эти команды обеспечивают наличие начальных данных в базе знаний, чтобы запросы по сущностям `Transformer`, `BERT`, `GPT` и другим базовым понятиям корректно обрабатывались системой.
